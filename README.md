
## 1. Выбор стека и подход к работе с видео

### Стек технологий
*   **Фреймворк:** **React** + **TypeScript**.
    *   *Обоснование:* Широкая экосистема, строгая типизация для надежного управления состоянием, отличная поддержка хуков для инкапсуляции логики плеера.
*   **Сборщик:** **Vite**.
    *   *Обоснование:* Мгновенный HMR и быстрая сборка критичны для итеративной разработки.
*   **Менеджер состояний:** **Zustand**.
    *   *Обоснование:* Легковеснее Redux, не требует `Provider`-ов на верхнем уровне, позволяет легко разделять сторы, идеально подходит для глобального состояния плеера (активное видео, состояние загрузки).
*   **Стилизация:** **CSS Modules** + **PostCSS**.
    *   *Обоснование:* Изоляция стилей на уровне компонентов без оверхеда CSS-in-JS во время выполнения.

### Работа с видео/медиа
*   **Плеер:** Нативный HTML5 `<video>`.
    *   *Обоснование:* Нет оверхеда от сторонних библиотек, полный контроль над API, возможность кастомизации буферизации и событий.
*   **Форматы:** **HLS (HTTP Live Streaming)** или **DASH**.
    *   *Обоснование:* Потоковая передача с адаптивным битрейтом (ABR) позволяет автоматически подстраивать качество под скорость интернета пользователя, экономя трафик. Backend отдает плейлист (`.m3u8` для HLS).
    *   *Альтернатива:* Если видео короткие (до 60 сек), можно использовать прогрессивную загрузку `mp4` с `byte-range` запросами, но HLS предпочтительнее для долгой работы.
*   **Буферизация (уровень плеера):**
    *   Используем `preload="metadata"`, чтобы не качать видео сразу при монтировании DOM.
    *   Управляем буфером через `video.buffered`. Как только активное видео начинает воспроизведение, мы вызываем `video.play()`, и браузер автоматически начинает наполнять буфер. Однако для контроля трафика мы можем ограничить буфер, используя свойство `buffer` в HLS.js (`maxBufferLength: 10` секунд), чтобы не перегружать память.

## 2. Механизм скролла и "залипание"

Вместо нативного скролла всей страницы мы используем **контейнер с фиксированной высотой (100dvh)** и **CSS Scroll Snap** в сочетании с программным управлением.

*   **Реализация:**
    *   Родительский контейнер: `height: 100dvh; overflow-y: scroll; scroll-snap-type: y mandatory;`.
    *   Дочерние элементы (слайды): `height: 100dvh; scroll-snap-align: start;`.
    *   Это дает плавный нативный скролл с "магнитным" эффектом бесплатно, без дерганья JS-анимаций.

*   **Обработка жестов (Свайп/Скролл):**
    *   Вешаем `onScroll` на контейнер с `throttle` (16мс для 60fps).
    *   Вычисляем текущий индекс: `Math.round(container.scrollTop / window.innerHeight)`.
    *   **"Залипание" (Snap):** Браузер делает это сам благодаря `scroll-snap-type`. Наша задача — не мешать ему.

*   **Детекция смены видео (Intersection Observer + Scroll-Listener):**
    *   Используем `IntersectionObserver` с `root: container` и `threshold: 0.6` (60% видимости) как *резервный* триггер.
    *   Основной триггер — `useEffect`, следящий за вычисленным `activeIndex`.
    *   При смене индекса:
        1. Ставим паузу текущему видео.
        2. Сбрасываем `currentTime` (опционально).
        3. Запускаем воспроизведение нового видео (если оно загружено).

## 3. Стратегия предзагрузки контента

### Количество элементов
*   Загружаем **2 элемента вперед** и **1 элемент назад** (относительно текущего индекса).
    *   *Обоснование:* Пользователь чаще скроллит вниз. 2 элемента гарантируют, что при быстром свайпе следующее видео будет готово мгновенно. 1 назад — для мгновенного возврата.

### Триггеры загрузки
1.  **Данные (Метаданные):** Загружаются пачкой (по 5-10 штук) при инициализации или при приближении к концу списка (Infinity Scroll).
2.  **Медиа-файлы (Видео):**
    *   **Холодная загрузка:** При монтировании компонента слайда в DOM (даже если он неактивен) устанавливаем `<video preload="metadata">`. Это получает размеры и длительность, но НЕ качает контент.
    *   **Горячая загрузка:** Как только слайд попадает в зону видимости (или за 1 шаг до нее), мы динамически меняем `preload="auto"` или, если используем HLS, инициируем загрузку сегментов через `hls.loadSource()`.
    *   *Альтернатива:* Использовать `IntersectionObserver` для каждого видео. Если видео пересекает границу `rootMargin: 200%`, мы начинаем подгрузку.

### Контроль нагрузки
*   Используем **Priority Queue** (очередь с приоритетом) для загрузки видео.
    *   Приоритет 1: Активное видео.
    *   Приоритет 2: Следующее (+1).
    *   Приоритет 3: Следующее (+2) и Предыдущее (-1).
*   Ограничиваем количество одновременных загрузок до **2** (чтобы не конкурировать за пропускную способность с активным видео).

## 4. Управление состоянием (State Management)

### Глобальный стор (Zustand)
Хранит данные, критичные для всей ленты:
```typescript
interface VideoStore {
  items: VideoItem[];        
  activeIndex: number;
  isLoading: boolean;
  isEndOfFeed: boolean;
  loadMore: () => Promise<void>;
  setActiveIndex: (index: number) => void;
  cache: Map<string, Blob>;   
}
```

### Локальное состояние (Компонент VideoPlayer)
Хранит состояние, уникальное для каждого плеера:
```
const [isPlaying, setIsPlaying] = useState(false);
const [progress, setProgress] = useState(0);
const [isBuffering, setIsBuffering] = useState(false);
const videoRef = useRef<HTMLVideoElement>(null);
```
*   *Обоснование:* Если бы мы хранили `isPlaying` для 10 видео в глобальном сторе, каждый скролл вызывал бы ре-рендер 10 компонентов. Храня это локально + используя `React.memo`, мы сводим ре-рендеры к минимуму.

### Кэширование просмотренного
*   **In-memory кэш:** Используем `Map` (в сторе) или `WeakMap` для хранения загруженных `Blob` URL'ов (через `URL.createObjectURL`).
*   **Persistent кэш:** Используем **Cache API** (Service Worker) для кэширования сегментов HLS. Это позволяет при повторном заходе на видео не качать его заново, если оно еще в кэше браузера.
*   **Позиция воспроизведения:** Храним `currentTime` в сторе, привязанную к `id` видео. Если пользователь вернулся к видео спустя 5 слайдов, оно продолжается с того же места (как в TikTok).

## 5. Производительность

### Виртуализация (React Virtuoso / react-window)
*   В отличие от горизонтальных таблиц, здесь мы не можем использовать `react-window` в классическом виде (из-за Scroll Snap).
*   **Решение:** Рендерим только **5 DOM-элементов** (активный + 2 вверх + 2 вниз).
    *   Остальные элементы заменяются на `div`-заглушки с той же высотой.
    *   При скролле мы переиспользуем DOM-узлы: когда элемент уходит из зоны видимости далеко, мы отсоединяем его видео-ноду и присоединяем ее к новому элементу внизу (Pooling).
    *   *Реализация:* Используем кастомный хук `useVideoPool`, который управляет `ref`-ами.

### Борьба с ре-рендерами
1.  **React.memo** для компонента `VideoItem`. Сравнение по `isActive`.
2.  **useCallback** для обработчиков событий (onPlay, onPause, onTimeUpdate), передаваемых в дочерние компоненты.
3.  **Разделение сторов:** Стор ленты (индексы) и стор данных (список видео) разделены, чтобы изменение прогресса одного видео не дергало весь список.

### Поведение при быстром скролле
*   При быстром скролле (инерция) мы **отключаем воспроизведение** на промежуточных видео.
*   Используем `scrollend` событие (современные браузеры) или таймер по окончанию скролла (`setTimeout` с очисткой).
*   *Логика:* При быстром скролле мы не вызываем `video.play()` на каждом промежуточном индексе, а ждем остановки. Если остановка произошла на индексе N — запускаем воспроизведение.

## 6. Улучшения по сравнению с существующими аналогами

1.  **Умная предзагрузка на основе поведения:**
    *   Если пользователь смотрит видео до конца (досматривает 100%), мы увеличиваем приоритет загрузки следующего видео до максимума.
    *   Если пользователь быстро листает (свайп каждую секунду), мы *понижаем* качество (битрейт) для превью, чтобы сэкономить трафик.

2.  **Аудио-фокус и "Picture-in-Picture" (PiP):**
    *   Автоматически приостанавливать видео, если пользователь переключил вкладку (используя `document.hidden`), и возобновлять при возврате.
    *   При нажатии на иконку PiP позволять видео "вылетать" в отдельное окно, продолжая играть, даже если пользователь скроллит дальше (это отсутствует в TikTok Web).

3.  **Прогрессивная деградация качества (LQIP):**
    *   Пока загружается HD-видео, показываем первый ключевой кадр (спрайт-превью) в виде статичного изображения (JPEG/WebP), наложенного поверх плеера. Это создает ощущение мгновенной загрузки, даже если трафик медленный.

4.  **Гибридный Scroll Snap:**
    *   Добавляем кнопки (навигационные точки) сбоку. При нажатии на точку мы не просто меняем индекс, а анимируем скролл с помощью `smooth` поведения, чтобы не перебивать нативную физику скролла.

5.  **Предзагрузка следующего видео со звуком:**
    *   В текущих реализациях звук включается только после старта видео. Я бы реализовал **AudioContext** для плавного "fade-in" звука при переходе, чтобы переход был менее резким на слух.

## 7. Архитектурная схема

```

const useVideoPlayer = (src: string, isActive: boolean) => {
  const videoRef = useRef<HTMLVideoElement>(null);
  const [isReady, setIsReady] = useState(false);

  useEffect(() => {
    if (isActive && isReady) {
      videoRef.current?.play().catch(() => {}); 
    } else {
      videoRef.current?.pause();
    }
  }, [isActive, isReady]);

  return { videoRef, setIsReady };
};

const Feed= () => {
  const { items, activeIndex, setActiveIndex } = useFeedStore();
  const containerRef = useRef<HTMLDivElement>(null);

  const handleScroll = useCallback(() => {
    const container = containerRef.current;
    if (!container) return;
    const newIndex = Math.round(container.scrollTop / window.innerHeight);
    if (newIndex !== activeIndex) {
      setActiveIndex(newIndex);
    }
  }, [activeIndex]);

  return (
    <div ref={containerRef} onScroll={handleScroll} style={{ height: '100dvh', overflowY: 'scroll', scrollSnapType: 'y mandatory' }}>
      {items.map((item, index) => {
        if (Math.abs(index - activeIndex) > 3) return <div key={item.id} style={{ height: '100dvh' }} />;
        return <VideoItem key={item.id} src={item.url} isActive={index === activeIndex} />;
      })}
    </div>
  );
};
```

## Итог

Данный план базируется на принципах **минимального оверхеда**, **нативной производительности браузера** (Scroll Snap, Video API) и **интеллектуальной буферизации**. Основной упор сделан на разделение ответственности (глобальное состояние для навигации, локальное для плеера) и адаптивную стратегию загрузки, которая не убивает батарею и трафик пользователя.

Реализация такого подхода гарантирует плавную работу на устройствах среднего класса и предсказуемое поведение при любых сценариях скролла.
